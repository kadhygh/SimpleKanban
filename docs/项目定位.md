# SimpleKanban 项目定位

最后更新：2026-03-09

## 1. 为什么这个项目重要

这几轮真实使用后，一个结论已经越来越清楚：

- `CLI` 很强，适合执行；
- 对话很灵活，适合推进单步任务；
- 但对人类来说，**长期上下文和整体结构并不适合只靠聊天记录承载**。

当任务跨天、跨阶段、跨多个终端会话时，人会很快遇到几个问题：

- 前面到底做到了哪里；
- 哪些能力已经实现，哪些只是讨论过；
- 哪些节点已经过本人验证，哪些还只是开发侧自测；
- 当前项目结构、任务结构、执行结构之间是什么关系；
- 下一步应该从哪一个最小节点继续接上。

这些问题并不是 `CLI` 本身不够强，而是因为：

**执行能力不等于上下文承载能力。**

SimpleKanban 的重要性，就在于它不是单纯再包一层终端，而是在尝试补上 AI 开发工作流里的一个关键断层：

**让人类能够持续看见结构、接住上下文、驾驭 LLM 的执行过程，而不是在文本洪流里迷路。**

## 2. 当前核心判断

### 2.1 单有 CLI 不够

`CLI` 非常适合：

- 启动任务；
- 执行命令；
- 获取即时输出；
- 与 LLM 工具直接交互。

但 `CLI` 不擅长天然表达这些内容：

- 任务之间的关系；
- 当前阶段的整体地图；
- 历史推进脉络；
- 哪一步已经被本人确认；
- 哪个执行入口对应哪个任务语义。

因此，SimpleKanban 不应该被理解为“把 terminal 放到网页里”，而应该被理解为：

**在保留 CLI 执行力的前提下，为人类补上一层结构化工作台。**

### 2.2 单有对话也不够

纯对话推进的问题在于：

- 单轮很顺；
- 多轮也能推进；
- 但一旦跨度拉长，人会迅速丢失整体感。

也就是说，对话适合“线性推进”，但不适合承担“项目地图”。

这也是为什么脑图、看板、结构图如此重要：

- 人类看图比看长对话更容易回忆结构；
- 人类看节点关系，比看文字滚动更容易找位置；
- 人类在图上更容易判断“现在在哪里”和“下一步去哪”。

## 3. SimpleKanban 真正要解决的问题

SimpleKanban 当前真正要解决的，不是“怎么运行一个 LLM CLI”，而是下面这件更大的事：

**怎样把 LLM 的执行能力、人的结构化理解能力、长期任务上下文、人工验证流程，放进同一个本地工作台。**

这件事可以拆成四层：

### 3.1 执行层

负责“真正做事”：

- 网页终端；
- PTY 会话；
- 执行器注入；
- 各类 CLI / 脚本运行。

### 3.2 结构层

负责“让人看懂”：

- 看板；
- 脑图；
- TaskCard；
- 节点之间的依赖与关系。

### 3.3 记忆层

负责“让人接得上”：

- 当前做到哪里；
- 为什么这么设计；
- 哪一步已经通过人工验证；
- 下一步应该延续哪个最小节点。

### 3.4 验证层

负责“让结果可信”：

- 开发侧自测；
- 用户本人验证；
- 验证通过前不提前标记完成；
- 每一步都能给出清晰的复现路径与预期结果。

## 4. 这个项目与普通任务面板的差异

普通任务面板通常只解决：

- 任务记录；
- 状态管理；
- 待办列表。

但 SimpleKanban 想做的是一个更完整的闭环：

1. **任务不是静态描述，而是执行入口。**
2. **执行不是黑盒，而是可观察终端会话。**
3. **终端不是孤立窗口，而是挂在项目上下文里的工作对象。**
4. **验证不是事后补充，而是流程闸门。**
5. **结构图不是附属展示，而是人类理解系统的主界面。**

因此，未来的 TaskCard 不只是“写一句需求”，而应该天然关联：

- 当前项目；
- 对应执行器；
- 当前终端会话；
- 输出产物；
- 人工验证结果；
- 与其他任务的关系。

## 5. 当前阶段已经验证出来的方向

到目前为止，已经有几件事通过真实使用被验证出来：

### 5.1 网页终端方向是对的

已经验证过：

- 创建网页终端；
- 在网页里输入输出；
- `resize`；
- 页面刷新后恢复终端连接。

这说明“网页托管终端会话”这条主路径成立。

### 5.2 执行器注入方向是对的

已经验证过：

- 执行器列表；
- 命令预览；
- 命令注入当前终端；
- 单参数输入控制最终生成的文档文件名。

这说明任务面板已经不只是“记录任务”，而是开始变成“可执行工作台”。

### 5.3 人工验证闸门是必要的

这几轮推进也证明：

- 仅靠开发侧自测不够；
- 仅靠“看起来合理”不够；
- 每个最小节点都要经过本人验证，项目节奏才稳。

这不是拖慢开发，而是在为长期演进建立可信基线。

## 6. 下一阶段的真正重点

接下来这个项目最重要的，不是立刻堆更多功能，而是继续把“结构层”和“记忆层”补起来。

优先级判断：

1. 继续保持最小节点推进与人工验证闸门；
2. 把执行结果与任务结构绑定起来；
3. 逐步引入更适合人理解全局的可视化结构；
4. 让“今天能执行”逐步升级成“过两天还能快速接上”。

换句话说，当前产品方向不应偏成：

- 一个更漂亮的终端；
- 一个更花哨的按钮面板；
- 一个单纯调用 LLM 的壳。

而应该继续朝这个方向走：

**一个让人类能够看见结构、调度执行、保存记忆、验证结果的本地 AI 工作台。**

## 7. 当前设计原则

基于现在的真实体感，后续实现应继续遵守这些原则：

- **结构优先于炫技**：优先让人看懂当前结构，而不是先堆复杂技术栈。
- **执行必须可见**：所有执行都应该尽量能回到当前终端或当前任务上下文中被观察。
- **验证必须落地**：没有本人验证通过的节点，不标记为完成。
- **最小节点推进**：每一步都尽量做到“小、可跑、可验证、可回退”。
- **本地优先**：当前阶段优先服务本地开发流，而不是远程协作大框架。
- **图形化是主界面方向**：脑图、节点图、看板是未来帮助人管理上下文的主路径。
- **任务、执行、记忆要逐步合流**：不要把它们做成三套彼此割裂的系统。

## 8. 一句话定义

SimpleKanban 不是“把 LLM CLI 放进网页里”的工具。

它更准确的定义应该是：

**一个面向本地开发流的 AI 工作台：用结构化界面承载任务与上下文，用网页终端承载执行，用人工验证保证结果可信。**
