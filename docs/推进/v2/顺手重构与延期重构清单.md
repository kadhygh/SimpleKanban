# 顺手重构与延期重构清单

这份清单用于约束 `v2` 当前阶段的推进方式：主线继续往前走，但只在“边界刚形成、尚未大面积铺开”的地方顺手重构；已经跑通且正在复测的主流程不回头大拆。

## 1. 当前判断

当前更合理的策略不是先做一次系统性重构，而是：

- 继续推进 `M8.2 ListWorkspace` 相关主线；
- 只在尚未大面积展开的边界层顺手重构；
- 把真正需要系统化整理的部分，留到 `M8.2` 稳定之后，再和后续 `DocCard` / `CanvasWorkspace` 一起收口。

原因：

- `v2` 的核心对象模型已经比较清楚，当前真正需要确认的是这条路线能不能稳定长出来；
- `parsed events`、多 `Session`、任务绑定即时同步已经过一轮验证，现阶段更应该把边界立正，再继续往监控面推进；
- 现在做大重构，最容易打断的反而是已经接近可持续推进的主流程。

## 2. 现在适合顺手重构的

下面这些点属于“边界刚形成，越早摆正越省后账”。

### 2.1 `Session` 结构化事件模型

适合现在做。

原因：

- 当前 `parsed events` 已经不只覆盖 `waiting / resumed`，而是开始具备最小生命周期事件；
- 这层如果继续自然生长，很容易变成零散字符串判断；
- 趁现在补齐基础事件，代价低，收益直接服务 `ListWorkspace` 监控。

当前已顺手推进：

- `session.started`
- `session.closed`
- `session.error`

后续再看是否补：

- `session.approval_required`
- `session.usage_updated`
- `session.agent_message`

### 2.2 `Session` 消息层和控制层边界

适合现在做。

原因：

- 当前系统已经有 WebSocket 输出、结构化事件、HTTP 控制接口和终端输入；
- 如果不趁早把 `stream / event / command response` 的边界分开，后续加 `ListWorkspace` 和更多监控时会越来越乱。

当前阶段的最低要求：

- 原始 PTY 输出继续保留；
- 结构化状态事件独立回流；
- 控制动作维持明确入口，不混成“伪消息”。

### 2.3 provider / executor adapter 入口

适合现在留接口，不适合现在做大实现。

原因：

- 当前还没有正式大规模引入多个本地 agent provider；
- 但如果前端开始直接理解 Codex / Claude 的差异，后面会更难收；
- 因此现在最合理的做法是预留 adapter 边界，而不是立刻重写执行层。

建议：

- 服务端逐步把“启动进程、解析输出、组装结构化消息”的逻辑收口到边界层；
- 前端只知道 `Session`，不知道 provider 细节。

### 2.4 `TaskCard` 运行态彻底绑定到 `Session`

适合现在继续收口。

原因：

- 文档里已经明确 `TaskCard` 的运行态来自绑定的 `Session`；
- 当前代码也已经往这个方向走了；
- 这类收口属于“让现有模型更一致”，不会改变用户工作流。

当前阶段应继续坚持：

- `workflowStatus` 由人工推进控制；
- `runtimeStatus` 由 session 真相回流；
- 不再让页面局部逻辑偷偷改写任务运行态语义。

## 3. 现在不适合回头重构的

下面这些内容一旦现在回头动，极容易打断主线。

### 3.1 已跑通并已验证通过的主流程

当前不应回头大动：

- `parsed events` 当前切口本身
- 绑定已有 `Session` 后任务运行态即时同步
- 已关闭 `Session` 上的输入守卫

原因：

- 这几块已经完成当前轮验证；
- 当前更应该把它们当作稳定基线继续向前推，而不是重新拆开。

### 3.2 现有 `CanvasWorkspace` 投影视图

当前不应为了“更优雅”回头重做。

原因：

- 当前主线还不在 `M8.4`；
- 现有 canvas 已能承担关系观察；
- 在 `ListWorkspace` 监控能力还没成型前，过早回头改 canvas 收益很低。

### 3.3 页面结构和视觉层细调

当前不应优先处理。

原因：

- 这类改动最容易消耗时间，却不增加结构稳定性；
- 目前更关键的是对象模型、运行态回流和监控可靠性。

## 4. 更适合 `M8.2` 之后统一重构的

下面这些内容值得做，但更适合在 `M8.2` 有了更稳定的监控面之后统一处理。

### 4.1 统一 store / 查询层

包括：

- `TaskCard / DocCard / Session` 的统一读取与投影；
- `ListWorkspace` 与 `CanvasWorkspace` 的共享查询模型；
- 更系统的派生状态组织方式。

原因：

- 现在这些视图边界还在生长；
- 太早抽象，容易抽错层。

### 4.2 更完整的 session 消息协议

包括：

- agent 消息
- usage
- approval request
- 摘要与结构化输出

原因：

- 目前只需要先把监控最关键的生命周期和等待态做稳；
- 更丰富的协议应建立在已验证的 session 事件模型之上。

### 4.3 更完整的执行层 adapter 化

包括：

- 多 provider
- 多 executor
- 输出协议统一
- 错误和权限模型统一

原因：

- 当前项目还没有进入“多 provider 真正并行使用”的阶段；
- 现在先立边界，比现在就上重构更合适。

## 5. 当前推进原则

接下来推进 `v2` 时，默认遵守下面 4 条：

1. 先推进主线，再顺手收边界，不做脱离里程碑的大重构。
2. 只重构“刚形成的边界层”，不重构“已经可用的主流程”。
3. 任何重构都要直接服务 `ListWorkspace` 监控能力或对象模型一致性。
4. 如果一个改动会明显打断当前推进路径，就推迟到 `M8.2` 之后。

## 6. 当前最合适的顺手推进项

上一轮最合适的一刀已经完成：

- 在现有 `parsed events` 上补了一层轻量的 `Session` 生命周期结构化事件；
- 让状态日志能更稳定地消费 `session.started / session.closed / session.error`；
- 继续保持原始终端输出和现有主流程不变。

接下来更合适的下一步是：

- 继续把 `ListWorkspace` 做成真正的监控和筛选面；
- 默认优先消费结构化 `Session` 事件，而不是继续依赖原始终端文本；
- 如果再补监控字段，也沿着当前 `Session` 真相回流方向推进。
