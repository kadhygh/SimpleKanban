# 修订版里程碑草案

最后更新：2026-03-12

## 1. 草案目标

这份草案用于承接 `v1` 之后的新方向：把当前系统从“单终端 + TaskCard + 结构投影”推进为“结构化 AI 工作台”。

这次修订的重点不是继续补一个更复杂的终端页，而是明确：

1. 哪些对象是系统的一等对象；
2. 哪些视图是给开发者观察和调度使用的；
3. 当前应优先补多 `session`，而不是完整终端历史；
4. `CanvasWorkspace` 和 `ListWorkspace` 应该如何分工。

## 2. 产品定位补充

`CanvasWorkspace` 与由 `TaskCard`、`DocCard` 构成的整个工作区，本质上是为了让开发者能够一目了然地观察、理解和调度。

它默认不是给 session 内 LLM 的完整上下文输入。

当前默认原则：

- `CanvasWorkspace` 主要服务于“人如何理解当前局面”；
- `TaskCard` 主要服务于“人如何推进工作项”；
- `DocCard` 主要服务于“人如何沉淀结构、说明、进度和 handoff”；
- `Session` 主要服务于“真实执行中的 shell / agent 上下文”。

允许的辅助能力：

- LLM 可以产出阶段总结、交接说明、提纲或拆解建议，再由开发者粘贴到 `DocCard`；
- 开启新 chat 时，开发者可以主动把某个 `DocCard` 的内容粘回去作为上下文；
- 未来可以增加一个以 `projectDir` 为操作范围的辅助 LLM，帮助生成 `DocCard` 骨架或任务拆解建议，但这不是当前前提。

## 3. 核心对象模型

### 3.1 TaskCard

`TaskCard` 表示一个工作项。

当前建议字段方向：

- `id`
- `title`
- `description`
- `workflowStatus`: `todo | doing | done`
- `executorId`
- `sessionId`: 绑定的主 `Session`
- `preferredWorkdir`: 创建新 `Session` 时的建议目录
- `dependencyIds`
- `attachments`

说明：

- `TaskCard` 的核心是“工作项”和“人工推进状态”；
- 不额外持久化一套独立的 `executionStatus`；
- 如果 `TaskCard` 绑定了 `Session`，它在 UI 上展示的运行态直接取自对应 `Session.runtimeStatus`。

### 3.2 DocCard

`DocCard` 表示结构化文档节点。

当前建议字段方向：

- `id`
- `title`
- `contentMd`
- `kind`: 例如 `note | plan | handoff | progress`
- `linkedTaskIds`
- `linkedSessionIds`
- `createdAt`
- `updatedAt`

说明：

- `DocCard` 用于承接需求拆解、阶段结论、授权说明、交接说明和下一步；
- `DocCard` 是独立对象，不再只是 `TaskCard.note` 的附属形态；
- 它首先服务于人，不默认自动同步给模型。

### 3.3 Session

`Session` 表示一个真实运行中的 shell / agent 上下文。

当前建议字段方向：

- `id`
- `name`
- `runtimeStatus`: `idle | running | waiting | closed | error`
- `workdir`
- `shell`
- `pid`
- `linkedTaskIds`
- `createdAt`
- `startedAt`
- `lastOutputAt`
- `endedAt`
- `exitCode`
- `error`

说明：

- `Session` 是一等对象；
- `workdir` 优先属于 `Session`，而不是 `TaskCard`；
- 多个 `TaskCard` 可以顺序复用同一个 `Session`；
- 第一版不做“每个 task 自动一个 session”。

## 4. 视图模型

### 4.1 CanvasWorkspace

`CanvasWorkspace` 是主工作面。

职责：

- 让开发者全局观察任务、文档和 session 的关系；
- 让开发者以空间化方式组织自己的工作流；
- 帮助开发者理解“现在哪些事情在推进、哪里卡住、哪些信息已经沉淀”。

不是它当前要做的事：

- 不是默认的 LLM 上下文输入面；
- 不是完整无限白板编辑器；
- 不是当前阶段的复杂手势系统实验场。

### 4.2 ListWorkspace

`ListWorkspace` 是监控和筛选面。

职责：

- 像 Jira 一样按规则筛选与监控；
- 支持手动添加监测区域；
- 快速看到“哪些 task / session 需要我立即响应”。

建议承载的信息：

- `workflowStatus`
- 绑定 `Session` 的当前运行态
- 是否 `waiting`
- 是否未绑定 `Session`
- 指定 `workdir` / `projectDir`
- 最近活动时间

说明：

- `CanvasWorkspace` 和 `ListWorkspace` 是同一套底层对象的两种视图；
- 它们不是两套独立的数据世界。

## 5. 当前优先级调整

当前优先级从高到低建议为：

1. 明确对象模型与双视图分工
2. 多 `Session` 最小闭环
3. `ListWorkspace` 监控能力
4. `DocCard` 最小闭环
5. `CanvasWorkspace` 基础可编辑化
6. 完整终端历史与更强上下文能力

当前明确后移的内容：

- 完整终端历史仓库
- 完整无限白板编辑器
- 复杂拖拽编排
- 复杂缩放 / 平移
- 完整连线编辑
- 每个 `TaskCard` 自动对应一个独立 `Session`

## 6. 修订后的里程碑

### M7.3 对象模型与双视图收口

状态：

- 已完成当前节点，并已由你本人于 `2026-03-12` 验证通过。

目标：

1. 正式确认核心对象为 `TaskCard`、`DocCard`、`Session`
2. 正式确认主要视图为 `CanvasWorkspace` 和 `ListWorkspace`
3. 明确 `TaskCard` 的人工状态与 `Session` 的运行状态分离
4. 明确 `CanvasWorkspace` 首先服务于开发者观察和调度，而不是默认喂给模型

非目标：

- 不做多 `Session` 实现
- 不做独立 `DocCard` 落库
- 不做完整白板编辑器

通过标准：

- 后续实现不再围绕“当前唯一终端页面”展开；
- 可以明确解释对象层和视图层的边界。

当前落地结果：

- 主页已按 `ListWorkspace` 收口；
- `CanvasWorkspace` 继续保留为关系观察面；
- `TaskCard` 已开始拆分 `workflowStatus` 与运行态展示；
- 后续推进锚点已切换到 `M8.1 多 Session 后端最小闭环`。

### M8.1 多 Session 后端最小闭环

目标：

1. 把当前单例终端管理器升级为 `Session Registry`
2. 第一版限制最多 3 个 `Session`
3. 支持创建、列出、关闭、按 id 连接 `Session`
4. 支持 `TaskCard` 绑定已有 `Session`，或新建 `Session` 后再绑定
5. 将 `waiting` 检测升级到按 `Session` 回流

非目标：

- 不做无限个 `Session`
- 不做每个 `TaskCard` 自动新建终端
- 不做完整终端历史

通过标准：

- 可以同时保持 2 到 3 个 `Session`；
- 可以明确知道每个 `TaskCard` 绑定的是哪个 `Session`；
- 某个 `Session` 等待人工处理时，相关任务能被提示出来。

### M8.2 ListWorkspace 最小闭环

目标：

1. 增加列表式监控工作区
2. 支持筛选器和手动监测区域
3. 一眼看到哪些任务在 `todo / doing / done`
4. 一眼看到哪些绑定的 `Session` 处于 `running / waiting / closed / error`
5. 支持从列表快速跳转到对应 `Session` 或 `TaskCard`

非目标：

- 不做复杂状态看板系统
- 不做多工程全量聚合大盘

通过标准：

- 开发者不进入终端页面，也能快速判断当前哪些地方需要自己介入。

### M8.3 DocCard 最小闭环

目标：

1. 引入独立 `DocCard`
2. 支持 Markdown 编辑与展示
3. 支持记录需求拆解、进度、handoff、关键说明
4. 支持在工作区中和 `TaskCard` 并列展示

非目标：

- 不做任意卡片类型系统
- 不做复杂块编辑器
- 不做自动摘要流水线

通过标准：

- 开发者可以先建 `DocCard` 梳理，再拆 `TaskCard`；
- 开发者可以把关键阶段说明沉淀为 `DocCard`，并在需要时手动复制给新的 chat。

### M8.4 CanvasWorkspace 基础可编辑化

目标：

1. 让 `CanvasWorkspace` 从投影视图变成真正的主工作面
2. 支持基础拖拽
3. 支持基础布局持久化
4. 能同时组织 `TaskCard` 和 `DocCard`

非目标：

- 不做完整无限白板系统
- 不做复杂手势和高阶交互

通过标准：

- 开发者可以根据自己的工作流组织工作区，而不是只能看系统给的固定投影。

### M9 历史与上下文增强

目标：

1. 增加 `Session` 输出持久化
2. 增加关键片段摘录
3. 增加 handoff 导出与归档
4. 视需要增加面向 `projectDir` 的辅助 LLM，帮助构建 `DocCard` 骨架

非目标：

- 不承诺自动读取全部历史对话
- 不追求一步到位复刻 Codex 式长期上下文系统

通过标准：

- 中断后恢复工作时，更多依赖结构化 `DocCard` 和摘要，而不是原始长日志。

## 7. 当前结论

当前最值得优先推进的不是完整终端历史，而是多 `Session`。

当前最合理的推进顺序是：

1. 先收口对象模型和双视图；
2. 再实现最多 3 个 `Session` 的最小池子；
3. 再让 `ListWorkspace` 承担监控与筛选职责；
4. 再把 `DocCard` 和 `CanvasWorkspace` 推成真正的主工作区。

一句话收口：

`v2` 的重点不再是“继续补一个更强的单终端页面”，而是“构建一个以 `TaskCard`、`DocCard`、`Session` 为核心、以 `CanvasWorkspace` 和 `ListWorkspace` 为主要视图的结构化 AI 工作台”。
